# Flapjack Audit — 2026-11-20

A thorough audit of the `@brandtg/flapjack` codebase (TypeScript feature-flags library + CLI, backed by PostgreSQL). Findings were verified empirically against a local Postgres container (host port 5433, db `flapjack_dev`) — not only by reading code. Nothing was fixed; this document is a report only.

- Repo: `@brandtg/flapjack` v1.5.0, HEAD `1794b2c`
- Working tree when audit began: clean
- Verification: `npm run build` (tsc) clean; `vitest run` on `src/cache.test.ts` (15 tests, passed), `src/model.test.ts` and `src/cli.test.ts` (155 + 7 tests, passed) — but **only after temporarily pointing the test files at the local dev DB port** (they hardcode `5432`, which is occupied in this environment; the files were reverted afterward)

## Severity legend

- **High** — correctness defect a user can hit in normal operation
- **Medium** — correctness/robustness issue or significant doc/behavior mismatch
- **Low** — inconsistency, doc drift, or hardening opportunity

## 1. `percent: 99.9` always passes — effective 100% rollout (verified)

- **Severity:** High
- **File:** `src/model.ts` (`evaluateFlagForUser`, lines ~598–605); `src/types.ts` (line 11); `migrations/1759720355601_create-feature-flag.js` (numeric(3,1) check `percent >= 0 AND percent <= 99.9`)
- **Evidence (runtime):** 10,000 synthetic users with `percent: 99.9` → 100.00% hit rate. With `percent: 50` → 49.98%. `percent: 0` → 0%.

`evaluateFlagForUser` computes the bucket as `hash % 100`, so a bucket ranges from 0–99. The rollout check is `bucket < flag.percent`. A value of `99.9` therefore passes for every bucket 0–99, i.e. 100% of users. Meanwhile `percent: 100` is rejected by the DB CHECK constraint (`numeric field overflow` / `percent >= 0 AND percent <= 99.9`), so a true 100% rollout cannot be expressed through the percentage path — the README tells you to do it anyway.

README.md line 357 (`percent: 100`) and line 517 ("5% → 25% → 50% → 100%") mis-instruct; line 117 documents `percent: 0-99.9`. `src/types.ts` line 11 says the same. The only way to roll the flag out to 100% is `everyone: true` — which the README documents as an override — but it does not say this is the 100% path.

**Fix direction:** either use a fractional bucket (e.g. `hash % 10000 < percent * 100`) so `99.9` is meaningfully ~99.9%, or cap the documented max at 99.9 and document that 100% requires `everyone: true`.

## 2. Expired flags evaluate normally when no `onExpired` handler is set (verified; contradicts the code comment and the test comment)

- **Severity:** Medium
- **File:** `src/model.ts` (`isActiveForContext`, lines ~712–722; also the identical block in `areActiveForContext`, lines ~843–851); `src/model.test.ts` (line ~1046–1051); `src/types.ts` lines 38–44

The code comment says "If the flag has expired, trigger event and return false". That is not what the code does:

```ts
if (
  this.eventHandlers?.onExpired &&
  flag &&
  flag.expires &&
  flag.expires <= new Date()
) {
  const expiredResult = await this.eventHandlers.onExpired({ flag });
  if (expiredResult !== undefined) return expiredResult;
}
// falls through to normal evaluation
```

When the model has no `onExpired` handler (the default), an expired flag is evaluated exactly as if it were unexpired. Verified: `everyone: true` + `expires` in the past → `isActiveForUser` returns `true`.

The `types.ts` doc comment (lines 38–44) states the intended behavior: "If it returns `undefined` the behavior will be the same as if the flag has not expired." — the code and the doc comment agree with each other, but the inline comment "If the flag has expired, trigger event and return false" is flat wrong.

The test in `src/model.test.ts` (line ~1046–1051) explicitly expects the fallthrough, and its comment contradicts its assertion:

```ts
// Default behavior: expired flags are not active
expect(isActive).toBe(true); // Should continue with normal evaluation
```

That test comment contradicts the assertion — a reader would expect `isActive` to be `false`. This is a doc/test-comment bug, not necessarily a behavior bug (the type-doc's "lenient" default is at least self-consistent), but the README never mentions expiry at all (see #9).

**Fix direction:** decide the intended default (strict: expired → false; lenient: expired → normal evaluation), say it in one place, and fix the comment(s) and the test comment.

## 3. `onExpired` fires only on cache miss (verified)

- **Severity:** Medium
- **File:** `src/cache.ts` (`FeatureFlagCache.isActiveForContext`, ~line 150–183); `src/model.ts` line ~712–722

`FeatureFlagCache` caches the boolean result. The `onExpired` handler is invoked inside `isActiveForContext`, inside the model, only on a cache miss. Verified with a 1-second TTL cache: call 1 → handler fires once; call 2 (cache hit) → handler does **not** fire again, and both calls return `true`.

Consequences:

- Handler side effects (metrics, alerts, cleanup) are only delivered on cache misses, not on every evaluation. With a long TTL the event effectively stops firing entirely.
- `expires` is not part of the cache key (only name/user/roles/groups/subjects), so a long-TTL cached entry for an expired flag keeps returning the cached value for the whole TTL even if the flag has since been modified to be non-expired or vice versa. Expiry is checked in the model, but only via the cache miss path.
- There is no way to invalidate a single flag's cache entry (`cache.clear()` nukes everything; the cache does not implement a tag/prefix invalidation).

## 4. `InMemoryCache` never sweeps expired entries (no periodic eviction or size bound)

- **Severity:** Medium
- **File:** `src/cache.ts` (`InMemoryCache`, lines ~24–62; no caller for `clearExpired()`)

Entries are removed lazily on `get()`. Expired entries whose keys are never queried are kept in the map forever — memory grows unboundedly with the number of distinct cache keys seen. A TTL of 60–300 seconds does not bound the memory of an unbounded key space.

`clearExpired()` exists but is not called by any production code path. A 5-minute TTL plus an unbounded `Map<string, ...>` is not a bounded cache.

**Fix direction:** periodic sweep (e.g. `setInterval(..., 60_000)` with `unref()`), a max-size LRU/FIFO bound, or an event-driven sweep on `set`. Document whichever you choose.

## 5. Cache key generation mutates caller arrays in place (verified)

- **Severity:** Medium
- **File:** `src/cache.ts` (`generateCacheKey`, lines ~114–116)

```ts
(roles || []).sort().join(","),
(groups || []).sort().join(","),
(subjects || []).sort().join(","),
```

Array `.sort()` sorts **in place** and returns the same reference. Callers that pass an array they keep using (e.g. "check flag A, then check flag B with the same roles array") get it reordered behind their back. Verified empirically: `roles: ["b", "a", "c"]` → `["a", "b", "c"]` after `isActiveForContext`; `groups` and `subjects` similarly reordered. (Note: the CLI's `is-active`/`are-active` commands do not reorder caller arrays because they build fresh `argv.roles` arrays from yargs each invocation; library callers who reuse an array do.)

This does not corrupt the key itself (a sorted key is still a stable key), but it's a surprising side effect to leak out of a pure-looking hashing function.

**Fix direction:** `[...roles].sort().join(",")` (or `roles.slice().sort()`).

## 6. Evaluation order documented in README disagrees with the model's doc comments and the actual code

- **Severity:** Medium
- **Files:** `README.md` lines ~112–118; `src/model.ts` lines ~646–652 (`isActiveForContext`) and ~750–756 (`areActiveForContext`); `src/model.ts` lines ~559–603 (actual evaluation order in `evaluateFlagForUser`)

README says (lines 112–118): everyone → users → groups → **subjects** → roles → percent → default.

`isActiveForContext` and `areActiveForContext` doc comments say (lines ~646–652 and ~750–756): everyone → users → groups → roles → percent → default — subjects omitted entirely.

Actual code in `evaluateFlagForUser` (lines ~559–603):

1. everyone override (lines ~560–563)
2. user match (lines ~565–567)
3. **subject** match via direct flag or flag-group (lines ~569–582)
4. **groups** match (lines ~585–587)
5. **roles** match (lines ~590–594)
6. **percent** rollout (lines ~598–605)
7. default false (line ~607)

So: the README places subjects between groups and roles (wrong), the doc comments omit subjects entirely (wrong), and the code places subjects between user and groups (correct). Pick one order — ideally the code's — and make all three agree, or drop the orderings.

## 7. `isActiveForUser` silently drops `subjects`

- **Severity:** Low
- **File:** `src/model.ts` lines ~671–691 (`isActiveForUser`, no `subjects` param) and ~783–798 (`areActiveForUser`, no `subjects` param)

Both "User" wrappers forward `{ name, user, roles, groups }` to their `Context` counterparts, silently discarding any `subjects` the caller might expect to flow through. The README documents only `isActiveForUser` in the API reference, so users who hit the API and assume "isActiveForUser" understands subjects will get a different result than if they called `isActiveForContext`. (The CLI's `is-active` / `are-active` commands use the User wrappers and expose no `--subjects` flag — only `is-active-context` / `are-active-context` do.) This is a documentation/naming gap rather than a code bug.

## 8. `hash-user` CLI command requires a database even though it is pure hashing (verified)

- **Severity:** Medium
- **File:** `src/cli.ts` (`hash-user` command, lines ~1458–1487)

The command is documented as "Hash a user ID using the same algorithm as percentage rollout" and works in the `npm run smoke` script. But the handler calls `createDatabase()` (which requires `DATABASE_URL`) before hashing, even though `hashUserId` is pure `MurmurHash3(userId).result()`. Verified:

- From the repo cwd with a `.env` present: `node dist/cli.js hash-user user123` → `{ "userId": "user123", "hash": 538840311, "bucket": 11 }`, exit 0
- From an arbitrary cwd without `.env`: `Error: DATABASE_URL is not set. Provide it in the environment or a .env file.`, exit 1 — the actual hash never runs

The `smoke` script passes only because it is run from the repo root. The command is misleading for anyone using the library without a database.

**Fix direction:** compute the hash from a local `new FeatureFlagModel({} as any)` / exported pure helper, or special-case `hash-user` to not create a pool.

## 9. Documentation gaps

- **Severity:** Low (a documentation inconsistency, but the README is the landing page)
- **File:** `README.md`

README has zero hits for `expires`, `onExpired`, or `expired`. The `onExpired` handler and the `expires` semantics (see #2) are nowhere documented — not as a feature list item, not in the API reference, not in the usage examples, not in the error-handling tips.

The README documents `archive` in the API reference (line 399–403) with usage notes, plus `archive` in the CLI (line 459) and the same semantics for groups (line 474). It does not document the expiry path at all.

The README documents `subjects` in one dedicated section (lines 121–167) — but the `isActiveForUser` API reference (line 405) does not mention subjects, and the two evaluation-order lists (lines 112–118 and the model doc comments) disagree (see #6).

The README documents `hashUserId` in the API reference as a one-liner (lines 409–411) and shows it in CLI usage (lines 492, 607); it does not document `areActiveForContext`, `areActiveForUser`, `getLastModified`, `getManyByName`, `getMany`, `updateAll`, `getGroupsForSubject`, `getFeatureFlagsForSubject`, or `isActiveForContext` in the API reference. `isActiveForContext` is mentioned in usage examples (lines 71, 144) and in the CLI docs (line 444) but never in the API reference. `listByTag` is documented in both the API reference (line 387) and usage examples (lines 199, 387).

The README also claims "**Battle-tested**: Comprehensive test suite with 31+ tests" (line 17). The actual test count is **177 tests** across three files (155 in `model.test.ts`, 7 in `cli.test.ts`, 15 in `cache.test.ts`). The "31+" number is stale by more than 5×.

The README's "How Feature Flag Evaluation Works" section (lines 112–118) lists subjects between groups and roles (wrong — see #6). The CLI does not document the evaluation order anywhere.

## 10. README example tells you to roll out to 100% (mathematically impossible)

- **Severity:** Medium (same underlying defect as #1, but worth calling out the docs separately)
- **File:** `README.md` lines 352–357 (the `percent: 100` example) and 517 (the "5% → 25% → 50% → 100%" rollout sequence)

See #1 for the verified behavior. The examples `percent: 100` will fail with a Postgres `numeric field overflow` error from the DB, not a clean 100% rollout.

## 11. `InMemoryCache` TTL is effectively unbounded on a long-running process (no max-entry bound)

- **Severity:** Low
- **File:** `src/cache.ts` (`InMemoryCache`, lines 20–62; no max-size)

The TTL only bounds entry lifetime, not total entry count. A long-running process that sees many distinct flag/user/roles/subjects combinations accumulates entries at roughly (distinct-keys × average-TTL-residency). Either sweep periodically, or cap the size.

## 12. Tests hardcode `localhost:5432` and fail when the dev DB port is occupied

- **Severity:** Low (test-environment friction, not a correctness bug in the library)
- **Files:** `src/model.test.ts` line 10; `src/cli.test.ts` line 14; `docker-compose.yml` (5432:5432; see #13)

The tests connect to `localhost:5432`. In this environment port 5432 is occupied by an unrelated service (`wisy-cloud-db-1`); the `flapjack` role password auth fails against it. The docker-compose dev stack also binds 5432:5432, so `npm run dev:docker:up` will fail with `port already in use`.

This is not a library bug, but it does mean the test suite is not portable and the developer experience is hostile. Test files should read `DATABASE_URL` or use an env-var override; docker-compose could read the port from the env too.

## 13. `.env` file points at the wrong port

- **Severity:** Low (environment-specific)

`.env` contains `DATABASE_URL=postgres://flapjack:flapjack@localhost:5432/flapjack_dev`. The working dev database in this environment is the container published on host port 5433. ## 14. Per-call round-trips in the unchached default path

- **Severity:** Low
- **File:** `src/model.ts` (`isActiveForContext`, lines ~693–731; `areActiveForContext`, lines ~805–863)

`areActiveForContext` passes one precomputed `subjectMatchedFlagIds` set to every `evaluateFlagForUser` call — good — and only calls `getSubjectMatchedFlagIds` once per evaluation, returning an empty set early when `subjects` is undefined or empty. The batch path is therefore efficient.

The per-flag path (`isActiveForContext` / `isActiveForUser`) does one DB round-trip for the flag plus one for the subject-match set (and `evaluateFlagForUser` will re-fetch the subject set only if the caller did not pass `subjectMatchedFlagIds` — which is not the case on the `isActiveForContext` path; it is always passed). The README warns about this explicitly — without caching, every `isActiveForUser()` call queries the database. For high-traffic flags the `FeatureFlagCache` layer is the intended escape hatch. This is fine as a design; it is worth noting the cache layer does not deduplicate flag metadata across different users.

## 15. Naming/API: four near-identical wrappers, two of which silently drop `subjects`

- **Severity:** Low
- **File:** `src/model.ts` lines ~671–691 (`isActiveForUser` → `isActiveForContext`) and ~783–798 (`areActiveForUser` → `areActiveForContext`)

Four evaluation entry points exist in the public API: `isActiveForUser`, `isActiveForContext`, `areActiveForUser`, `areActiveForContext`. Each `User` wrapper delegates to its `Context` counterpart with the `subjects` argument dropped (see #7). Both `Context` methods carry duplicated doc-comments (lines ~646–652 and ~750–756) that omit `subjects` from the evaluation-order list (see #6). The README documents `isActiveForUser` in the API reference; `isActiveForContext` is mentioned only in usage examples; `areActiveForContext` and `areActiveForUser` are not documented.

## 16. Index coverage is mostly sound (no real gap found)

- **Severity:** Low (informational)
- **Files:** `migrations/1779210257698_add-feature-flag-subjects.js`; `migrations/1781107651000_add-feature-flag-tags.js`; `migrations/1764560643657_add-feature-flag-groups.js`; `src/model.ts` lines ~502–528

The flag-subject and group-subject tables both have indexes on `subject` (migration 1779210257698, lines 39–43 and 75–79), so the `getSubjectMatchedFlagIds` query (`WHERE subject = ANY($1)`) is indexed. `feature_flag` is unique on `name`. The subject tables are unique on `(feature_flag_id, subject)` and `(feature_flag_group_id, subject)`. Tags have a GIN index (migration 1781107651000). Groups have indexes on `group_id` and `feature_flag_id` (migration 1764560643657).

No real missing-index gap was found:
- `list()`, `getById`, `getByName`, `getManyByName`, `getMany` are indexed on the primary key / `name` (the `includeArchived` filter is a `WHERE archived IS NULL` on the same indexed columns).
- `getFeatureFlagsForSubject` (`WHERE s.subject = $1`) is indexed (subject index above).
- `getGroupsForSubject` (`WHERE gs.subject = $1`) is indexed (subject index above).

One worth-noting performance point: `areActiveForContext` calls `getSubjectMatchedFlagIds` once per evaluation and reuses the set across every flag — good — and `getSubjectMatchedFlagIds` returns an empty set early when `subjects` is empty. The per-flag path (`isActiveForContext`) repeats one flag fetch plus one subject-match fetch per call; that is the intended reason the README points high-traffic consumers at the `FeatureFlagCache` layer.

## 17. Miscellaneous / hardening

- **No input validation** in `create`/`update` (`src/model.ts`): name can be empty, percent can be negative in code path (the DB CHECK catches it, but the error surfaces as a raw Postgres exception rather than a friendly error), `expires` can be in the past (allowed by design). The CLI exposes `--expires` as a raw string and casts it with `new Date(argv.expires)` (`src/cli.ts`, lines 105 and 330) — an unparseable value yields `Invalid Date`, which Postgres rejects with error `22007` (`invalid input syntax for type timestamp with time zone`) rather than silently coercing. The `expires` column is nullable, so `null` is a legal escape hatch; the CLI provides `--clear-expires` to set it (src/cli.ts, line 283) but the `create` command has no way to clear it (there is no `create`-side clear, and a `--expires` in the past is silently accepted).
- **`process.exit(1)` in CLI handlers** — the CLI exits on any handler throw; this is the intended pattern for a CLI entry point, but errors in the top-level `.catch` (unhandled) also produce a stack trace and exit 1 (verified). Libraries should not call `process.exit`; a library-exportable CLI would be nicer, but that's a product decision.
- **`InMemoryCache.size()`** (`src/cache.ts`, ~line 63) reports `cache.size()` of the underlying map, including expired entries that have not yet been read or swept — callers can read a misleading number.
- **`InMemoryCache` does not validate TTL** — negative or zero TTL produces an entry with `expiresAt <= now` and effectively a cache that never hits.
- **`MurmurHash3` shared state**: `imurmurhash` creates a static cached object via `MurmurHash3(userId).result()` when called without `new`. Sync, so no interleaving hazard in the current evaluation path, but fragile if hashing were made async.
- **`evaluateFlagForUser` (`src/model.ts`, line 543) is public** — the class is exported from `src/index.ts`, so callers can invoke it directly with a flag they have fetched. That path skips the `getByName` archived-exclusion check and the `getSubjectMatchedFlagIds` early-return when `subjectMatchedFlagIds` is omitted (in which case it re-queries subject matches via a private method). It is not re-exported through `src/index.ts` and is not documented in the README. Either document it (or make it `private`) or accept that it is an implementation detail.
- **CLI `--percent` is typed as `number`** with no validation (`src/cli.ts`, lines 41 and 1222); DB CHECK catches out-of-range values, but the error surfaces as a raw Postgres exception (`numeric field overflow` / `check constraint`) rather than a friendly CLI error.
