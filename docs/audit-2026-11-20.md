## 1. `percent: 99.9` always passes — effective 100% rollout (verified)


- **Severity:** High
- **File:** `src/model.ts` (`evaluateFlagForUser`, lines ~598–605); `src/types.ts` (line 11); `migrations/1759720355601_create-feature-flag.js` (numeric(3,1) check `percent >= 0 AND percent <= 99.9`)
- **Evidence (runtime):** 10,000 synthetic users with `percent: 99.9` → 100.00% hit rate. With `percent: 50` → 49.98%. `percent: 0` → 0%.

`evaluateFlagForUser` computes the bucket as `hash % 100`, so a bucket ranges from 0–99. The rollout check is `bucket < flag.percent`. A value of `99.9` therefore passes for every bucket 0–99, i.e. 100% of users. Meanwhile `percent: 100` is rejected by the DB CHECK constraint (`numeric field overflow` / `percent >= 0 AND percent <= 99.9`), so a true 100% rollout cannot be expressed through the percentage path — the README tells you to do it anyway.

README.md line 357 (`percent: 100`) and line 517 ("5% → 25% → 50% → 100%") mis-instruct; line 117 documents `percent: 0-99.9`. `src/types.ts` line 11 says the same. The only way to roll the flag out to 100% is `everyone: true` — which the README documents as an override — but it does not say this is the 100% path.

**Fix direction:** either use a fractional bucket (e.g. `hash % 10000 < percent * 100`) so `99.9` is meaningfully ~99.9%, or cap the documented max at 99.9 and document that 100% requires `everyone: true`.


### TODO

- [x] Decide the target behavior: fractional-bucket percentage (e.g. `hash % 10000 < percent * 100`) vs. keep `bucket = hash % 100` and document 99.9 as the effective max. — Decision: keep `hash % 100` buckets and document 99.9 as the effective max (no behavior change, no migration).
- [x] Implement the chosen fix in `src/model.ts` (`evaluateFlagForUser`, lines ~598–605) and `src/types.ts` (percent type/comment). — Doc comment in `evaluateFlagForUser`, `hashUserId` @remarks, `create()` @param, and `types.ts` percent comment updated; the comparison logic was kept as `bucket < percent`.
- [x] Decide whether the DB CHECK constraint should change from `percent <= 99.9` to `percent <= 100` (and add an accompanying migration if so). — Decision: no change. 99.9 remains the effective max; `percent: 100` is rejected by the CHECK constraint; `everyone: true` is the 100% path.
- [x] Update README lines 352–357 and 517 (percent rollout example and sequence), and the `types.ts` percent comment. — README example now uses 5% → 25% → 50% → `everyone: true`; line 522 rollout sequence now ends at 99.9%; `How User Bucketing Works` and the evaluation-order list document the 99.9 effective max.
- [x] Add/extend tests covering `percent: 99.9`, `percent: 100`, and boundary values (0, 0.1, 50.0, 99.9, 100). — New `percentage rollout bounds` describe block (6 tests): 0, 99.9, 0.1, 50, 100 (rejected by CHECK), and everyone-override-over-percent.
- [x] Verify against the local dev DB (port 5433) and re-run `npm run build` + `vitest run`. — Build clean; `model.test.ts` 161/161 passed, `cli.test.ts` + `cache.test.ts` 22/22  passed (tests temporarily pointed at 5433, then reverted to 5432 as in the original audit).

### Implementation notes

- 2026-11-20: Kept `hash % 100` buckets and documented 99.9 as the effective max rather than switching to fractional buckets (fractional-bucket change would break existing bucket assignments). Doc comments + README + CLI descriptions updated; new `percentage rollout bounds` tests added. Verified against local dev DB on port 5433 (tests pointed there temporarily, then reverted): 161 model tests + 22 cli/cache tests pass; `npm run build` clean.

## 2. Expired flags evaluate normally when no `onExpired` handler is set (verified; contradicts the code comment and the test comment)


- **Severity:** Medium
- **File:** `src/model.ts` (`isActiveForContext`, lines ~712–722; also the identical block in `areActiveForContext`, lines ~843–851); `src/model.test.ts` (line ~1046–1051); `src/types.ts` lines 38–44

The code comment says "If the flag has expired, trigger event and return false". That is not what the code does:

```ts
if (
  this.eventHandlers?.onExpired &&
  flag &&
  flag.expires &&
  flag.expires <= new Date()
) {
  const expiredResult = await this.eventHandlers.onExpired({ flag });
  if (expiredResult !== undefined) return expiredResult;
}
// falls through to normal evaluation
```

When the model has no `onExpired` handler (the default), an expired flag is evaluated exactly as if it were unexpired. Verified: `everyone: true` + `expires` in the past → `isActiveForUser` returns `true`.

The `types.ts` doc comment (lines 38–44) states the intended behavior: "If it returns `undefined` the behavior will be the same as if the flag has not expired." — the code and the doc comment agree with each other, but the inline comment "If the flag has expired, trigger event and return false" is flat wrong.

The test in `src/model.test.ts` (line ~1046–1051) explicitly expects the fallthrough, and its comment contradicts its assertion:

```ts
// Default behavior: expired flags are not active
expect(isActive).toBe(true); // Should continue with normal evaluation
```

That test comment contradicts the assertion — a reader would expect `isActive` to be `false`. This is a doc/test-comment bug, not necessarily a behavior bug (the type-doc's "lenient" default is at least self-consistent), but the README never mentions expiry at all (see #9).

**Fix direction:** decide the intended default (strict: expired → false; lenient: expired → normal evaluation), say it in one place, and fix the comment(s) and the test comment.


### TODO

- [x] Decide the intended default for an expired flag with no `onExpired` handler (strict: expired → false; lenient: fall through to normal evaluation). — Decision: strict. An expired flag is inactive regardless of normal rules. (Superseded 2026-11-21 — see finding #18: strict default removed; expiry is signal-only and `everyone` wins.)
- [x] Implement the chosen behavior in `src/model.ts` (`isActiveForContext` ~712–722 and the identical block in `areActiveForContext` ~843–851). — Both blocks now return false when the flag is expired unless the handler returns a boolean. (Superseded 2026-11-21 — see finding #18.)
- [x] Fix the inline comment and the misleading test comment in `src/model.test.ts` (~1046–1051). — Inline comment updated to describe the new behavior; the "no handler" test now asserts `false` and adds role-match and areActiveForUser variants. (Superseded 2026-11-21 — see finding #18.)
- [x] Document the semantics in `src/types.ts` (lines 38–44) if the chosen behavior differs from the current one. — `types.ts` handler doc now states an `undefined` return treats the flag as inactive. (Superseded 2026-11-21 — see finding #18.)
- [x] Add/extend tests for the chosen default and for the `onExpired` handler path. — Existing handler tests updated to expect `false` when the handler returns `undefined`; new no-handler tests added. (Superseded 2026-11-21 — see finding #18.)
- [x] Verify against the local dev DB (port 5433) and re-run `npm run build` + `vitest run`. — Build clean; `model.test.ts` 163/163 passed, `cli.test.ts` + `cache.test.ts` 22/22  passed (tests pointed at 5433 temporarily, then reverted).

### Implementation notes

- 2026-11-20: Chose strict default (expired → false even without a handler). Both evaluation paths in `src/model.ts` updated; `types.ts` doc updated; handler tests and no-handler tests updated to match. Verified against local dev DB on port 5433: 163 model tests + 22 cli/cache tests pass; `npm run build` clean. (Superseded 2026-11-21 — see finding #18.)

## 3. `onExpired` fires only on cache miss (verified)


- **Severity:** Medium
- **File:** `src/cache.ts` (`FeatureFlagCache.isActiveForContext`, ~line 150–183); `src/model.ts` line ~712–722

`FeatureFlagCache` caches the boolean result. The `onExpired` handler is invoked inside `isActiveForContext`, inside the model, only on a cache miss. Verified with a 1-second TTL cache: call 1 → handler fires once; call 2 (cache hit) → handler does **not** fire again, and both calls return `true`.

Consequences:

- Handler side effects (metrics, alerts, cleanup) are only delivered on cache misses, not on every evaluation. With a long TTL the event effectively stops firing entirely.
- `expires` is not part of the cache key (only name/user/roles/groups/subjects), so a long-TTL cached entry for an expired flag keeps returning the cached value for the whole TTL even if the flag has since been modified to be non-expired or vice versa. Expiry is checked in the model, but only via the cache miss path.
- There is no way to invalidate a single flag's cache entry (`cache.clear()` nukes everything; the cache does not implement a tag/prefix invalidation).


### TODO

- [x] Decide what `onExpired` should mean in the cached path — fires on every evaluation, including cache hits.
- [x] Decide whether `expires` should be part of the cache key — no: the key is unchanged. Entries store the flag's expiry (epoch ms) alongside the result; staleness is bounded by the TTL.
- [x] Implement the chosen behavior in `src/cache.ts` (`FeatureFlagCache.isActiveForContext`). — Entries now store `{ result, flagExpires }` (not the whole flag). On a cache hit, if the stored expiry is in the past, the cached flag is fetched fresh and the model's shared `fireExpiredHandler` is called (same helper the model's evaluation paths use). The cached boolean result stands; the handler's return value is ignored on cache hits. Non-expired hits never touch the DB. The miss path stores the expiry after the model returns (one extra indexed `getByName` per miss).
- [x] Add/extend tests for the cached expired-flag path (cache hit/miss, flag modification after first evaluation). — New tests: handler re-fires on every hit (including the second+); handler return value ignored on hit; non-expired cached flag never triggers a fetch/fire; null-flag entries skip firing; fresh flag is re-read on a stale-expiry hit (modified flags); handler fires zero times on the miss path (the model's own evaluation already fired it); legacy boolean entries from a pre-change deploy cache are accepted as-is.
- [x] Verify against the local dev DB (port 5433) and re-run `npm run build` + `vitest run`. — Build clean; `model.test.ts` 163/163, `cache.test.ts` 22/22, `cli.test.ts` 7/7 (tests pointed at 5433 temporarily, then reverted).

### Implementation notes

- 2026-11-20: Cache layer reuses the model's new public `fireExpiredHandler(flag)` helper — the same code path as the model's `isActiveForContext`/`areActiveForContext` expired-block — so a cache hit fires the same handler with a freshly-read flag. `CachedFlagResult` is exported from `src/index.ts`; README's cached-instance examples updated (`new InMemoryCache<CachedFlagResult>()`, Redis example implements `Cache<CachedFlagResult>`). Handler return value on a hit is ignored by design (the cached result stands); staleness within the TTL is bounded by the TTL. Entries are JSON-safe (`{ result, flagExpires: epoch ms | null }`) and legacy bare-boolean entries from a pre-change deploy cache are accepted and returned as-is (parsed as `{ result, flagExpires: null }`), so no cache nuke is needed at deploy time.

## 4. `InMemoryCache` never sweeps expired entries (no periodic eviction or size bound)


- **Severity:** Medium
- **File:** `src/cache.ts` (`InMemoryCache`, lines ~24–62; no caller for `clearExpired()`)

Entries are removed lazily on `get()`. Expired entries whose keys are never queried are kept in the map forever — memory grows unboundedly with the number of distinct cache keys seen. A TTL of 60–300 seconds does not bound the memory of an unbounded key space.

`clearExpired()` exists but is not called by any production code path. A 5-minute TTL plus an unbounded `Map<string, ...>` is not a bounded cache.

**Fix direction:** periodic sweep (e.g. `setInterval(..., 60_000)` with `unref()`), a max-size LRU/FIFO bound, or an event-driven sweep on `set`. Document whichever you choose.


### TODO

- [x] Decide the chosen eviction strategy — max-size bound (LRU), no periodic timer. `clearExpired()` stays public/test-only (no production caller); entries still expire lazily on `get()`.
- [x] Implement it in `src/cache.ts` (`InMemoryCache`) — constructor option `maxSize` (default `10_000`, exported as `DEFAULT_MAX_SIZE`, validated as a positive integer); a `set` that would exceed the bound drops expired entries first, then least-recently-used entries (refreshed on `get`/`set` of the same key). No `setInterval` — nothing holds the event loop open.
- [x] Decide whether `clearExpired()` should be called from the production path — kept public/test-only; lazy expiry on `get` + the bound on `set` cover the production path.
- [x] Add/extend tests for the new eviction behavior — max-size eviction, `get`/`set` recency refresh, expired-before-live eviction, invalid `maxSize`, and the 10k default bound.
- [x] Verify against the local dev DB (port 5433) and re-run `npm run build` + `vitest run`. — Build clean; `cache.test.ts` 28/28, `model.test.ts` 163/163, `cli.test.ts` 7/7 (tests pointed at 5433 temporarily, then reverted).

### Implementation notes

- 2026-11-20: `InMemoryCache` now takes `{ maxSize }` in the constructor (default `10_000`) with LRU eviction on `set` — expired entries dropped first, then the least-recently-used. A `get` is a recency refresh, and re-`set`ing an existing key re-inserts it. No timer — the event loop is never held open by the cache. `clearExpired()` is unchanged and remains public/test-only; `size()` still reports the raw map size (not sweep-adjusted), as documented. This is `InMemoryCache` only; the custom Redis cache in `README.md` stays upstream-owned and is not given a bound here (upstream decides how it bounds its own store). Implements the caller-visible shape (`new InMemoryCache({ maxSize })`) without changing the `Cache` interface.


## 5. Cache key generation mutates caller arrays in place (verified)


- **Severity:** Medium
- **File:** `src/cache.ts` (`generateCacheKey`, lines ~114–116)

```ts
(roles || []).sort().join(","),
(groups || []).sort().join(","),
(subjects || []).sort().join(","),
```

Array `.sort()` sorts **in place** and returns the same reference. Callers that pass an array they keep using (e.g. "check flag A, then check flag B with the same roles array") get it reordered behind their back. Verified empirically: `roles: ["b", "a", "c"]` → `["a", "b", "c"]` after `isActiveForContext`; `groups` and `subjects` similarly reordered. (Note: the CLI's `is-active`/`are-active` commands do not reorder caller arrays because they build fresh `argv.roles` arrays from yargs each invocation; library callers who reuse an array do.)

This does not corrupt the key itself (a sorted key is still a stable key), but it's a surprising side effect to leak out of a pure-looking hashing function.

**Fix direction:** `[...roles].sort().join(",")` (or `roles.slice().sort()`).


### TODO

- [x] Fix `src/cache.ts` `generateCacheKey`: sort copies, not references (`[...roles].sort().join(",")`).
- [x] Add a regression test asserting caller arrays are not reordered after `isActiveForContext` — the test also asserts the key is still order-insensitive (second call in different order hits the cache).
- [x] Verify against the local dev DB (port 5433) and re-run `npm run build` + `vitest run`. — Build clean; `model.test.ts` 163/163, `cache.test.ts` 29/29, `cli.test.ts` 7/7 (tests pointed at 5433 temporarily, then reverted).

### Implementation notes

- 2026-11-20: The three `.sort()` calls in `generateCacheKey` were the only in-place sorts in `src/` (model paths copy arrays for DB calls and never sort). `[...roles].sort()` — same `.sort()`, copied input — replaces each; the key itself is unchanged, so existing cache entries stay valid. Regression test in `src/cache.test.ts` asserts the caller arrays are untouched and that a different-order call still hits the cache.

## 17. Miscellaneous / hardening


- **No input validation** in `create`/`update` (`src/model.ts`): name can be empty, percent can be negative in code path (the DB CHECK catches it, but the error surfaces as a raw Postgres exception rather than a friendly error), `expires` can be in the past (allowed by design). The CLI exposes `--expires` as a raw string and casts it with `new Date(argv.expires)` (`src/cli.ts`, lines 105 and 330) — an unparseable value yields `Invalid Date`, which Postgres rejects with error `22007` (`invalid input syntax for type timestamp with time zone`) rather than silently coercing. The `expires` column is nullable, so `null` is a legal escape hatch; the CLI provides `--clear-expires` to set it (src/cli.ts, line 283) but the `create` command has no way to clear it (there is no `create`-side clear, and a `--expires` in the past is silently accepted).
- **`process.exit(1)` in CLI handlers** — the CLI exits on any handler throw; this is the intended pattern for a CLI entry point, but errors in the top-level `.catch` (unhandled) also produce a stack trace and exit 1 (verified). Libraries should not call `process.exit`; a library-exportable CLI would be nicer, but that's a product decision.
- **`InMemoryCache.size()`** (`src/cache.ts`, ~line 63) reports `cache.size()` of the underlying map, including expired entries that have not yet been read or swept — callers can read a misleading number.
- **`InMemoryCache` does not validate TTL** — negative or zero TTL produces an entry with `expiresAt <= now` and effectively a cache that never hits.
- **`MurmurHash3` shared state**: `imurmurhash` creates a static cached object via `MurmurHash3(userId).result()` when called without `new`. Sync, so no interleaving hazard in the current evaluation path, but fragile if hashing were made async.
- **`evaluateFlagForUser` (`src/model.ts`, line 543) is public** — the class is exported from `src/index.ts`, so callers can invoke it directly with a flag they have fetched. That path skips the `getByName` archived-exclusion check and the `getSubjectMatchedFlagIds` early-return when `subjectMatchedFlagIds` is omitted (in which case it re-queries subject matches via a private method). It is not re-exported through `src/index.ts` and is not documented in the README. Either document it (or make it `private`) or accept that it is an implementation detail.
- **CLI `--percent` is typed as `number`** with no validation (`src/cli.ts`, lines 41 and 1222); DB CHECK catches out-of-range values, but the error surfaces as a raw Postgres exception (`numeric field overflow` / `check constraint`) rather than a friendly CLI error.
